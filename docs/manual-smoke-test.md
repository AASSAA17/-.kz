# Ручная проверка MVP

Выполняйте сценарий на локальном компьютере с вымышленными именами и контактами. Список ниже — инструкция, а не утверждение, что все проверки уже проведены в вашем окружении.

## Подготовка

1. Установите зависимости: `npm install`.
2. Создайте настройки: `npm run setup`. Сохраните выведенный пароль администратора.
3. Запустите `npm run dev`, откройте `http://localhost:5173`.
4. Убедитесь, что каталог содержит пять площадок, фильтрация работает и карточки открываются.

## Заявка клиента

1. Откройте подходящую площадку.
2. Выберите будущую дату и доступное время продолжительностью один или два часа. Все часы бронирования относятся к Астане.
3. Проверьте, что сумма меняется при изменении длительности в соответствии с тарифом площадки.
4. Перейдите к контактам. Без отметки согласия отправка должна быть недоступна. Отметьте согласие и попробуйте отправить форму с пустыми обязательными полями: браузер должен запросить их заполнение, заявка не должна создаться.
5. Введите вымышленное имя и телефон в формате `+7 XXX XXX XX XX`, отправьте форму.
6. Убедитесь, что получено подтверждение создания заявки и индивидуальная ссылка вида `/booking/:token`. Сохраните её.
7. Откройте ссылку в другом окне: должны отображаться статус и условия бронирования, но не имя, телефон или комментарий клиента.

## Защита от пересечения

1. Откройте эту же площадку и дату в другом окне браузера.
2. Проверьте, что уже занятый интервал недоступен.
3. Дополнительно перед отправкой первой заявки можно открыть одну и ту же доступность в двух окнах: отправить заявку в первом, затем попытаться отправить пересекающуюся заявку во втором без обновления страницы.
4. Сервер должен отклонить вторую заявку, даже если второе окно показывало устаревшие свободные слоты.
5. Непересекающееся время той же площадки или тот же интервал другой площадки должны оставаться доступными.

## Администратор

1. Откройте `http://localhost:5173/admin`.
2. Попробуйте неверный пароль: список заявок не должен открыться.
3. Введите пароль из `.env`, найдите созданную заявку по поиску или фильтрам.
4. Подтвердите заявку и проверьте результат по клиентской ссылке.
5. Отмените тестовую заявку, указав причину, и обновите страницу выбора времени: её интервал должен освободиться.
6. Заблокируйте другое свободное время через административную страницу. Оно должно стать недоступно клиенту; после снятия блокировки — снова доступно.
7. Выйдите из административной сессии. Обновление страницы не должно возвращать доступ к данным без входа.

## Сохранение и сборка

1. Создайте ещё одну тестовую заявку.
2. Остановите приложение через `Ctrl+C`, затем снова выполните `npm run dev`.
3. Откройте административную страницу и убедитесь, что заявка сохранилась. Если истёк срок ожидания, она должна остаться в списке с соответствующим статусом.
4. Остановите режим разработки, выполните `npm run build`, затем `npm start`.
5. Откройте `http://localhost:3001`, повторите просмотр каталога и административный вход.
6. Проверьте прямое открытие `/admin`, `/locations/:id` и сохранённой ссылки заявки, а также обновление этих страниц в браузере.

## Что записать при ошибке

Запишите шаг, ожидаемый и фактический результат, адрес страницы, дату и время заявки, браузер и текст ошибки из терминала. Не включайте в отчёт пароль из `.env`, cookie сессии и настоящие контактные данные.

## Автоматические проверки

`npm test` запускает интеграционные тесты API на отдельных временных базах. `npm run build` проверяет сборку интерфейса. Обе команды можно запускать без создания `.env`. Они дополняют ручной сценарий, но не заменяют визуальную проверку и проверку браузерного интерфейса.
