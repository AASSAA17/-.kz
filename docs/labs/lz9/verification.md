# Изменения сайта и проверка ЛЗ 9

## Реализованный пользовательский результат

После локальной демонстрационной регистрации и входа новые заявки связываются с ID текущего пользователя и видны в его кабинете. Второй аккаунт не получает эти заявки. Сопоставление по телефону или email не выполняется: прежние гостевые заявки доступны по личным ссылкам. Срок ожидания заявки обновляется при чтении кабинета теми же правилами, что и в публичном статусе. Вход и выход отражаются в навигации.

Демонстрационный код не называется SMS. В production без подключённого SMS-провайдера создание и подтверждение аккаунта возвращают понятную ошибку, интерфейс предлагает гостевое бронирование. Уже существующие подтверждённые аккаунты могут входить. В этой версии SMS-провайдер, повторная отправка и восстановление пароля не реализованы.

Счётчики неудачных попыток клиентского входа и подтверждения теперь сохраняются после завершения транзакции; ответ с ошибкой отправляется после записи. Пять неверных кодов блокируют этот код, пять неверных входов ограничивают последующие попытки в фиксированном 15-минутном окне. Ограничение переживает перезапуск SQLite.

Доска `/team.html` отделена от каталога и доступна по ссылке в подвале. Она сохраняет фактические переходы в браузере, проверяет WIP при ручном переводе, экспортирует историю и отчёт. Отдельный учебный набор показывает расчёт двух спринтов. Для статических `.mjs` сервер устанавливает JavaScript MIME, чтобы модули загружались и после production-сборки.

## Автоматические проверки

Команды: `npm test`, `npm run build`. Покрыты прежние сценарии бронирования и администратора, собственные и чужие заявки, повторная отправка и привязка к аккаунту, выход, одноразовый код, срок кода, счётчики и перезапуск. Расчёт потока проверяется на выходных, переносах, пустых периодах, WIP по времени, p85, отсутствии DoD и воспроизводимости симуляции. Сам текст ошибки или наличие галочки не заменяют независимую приёмку.

PostgreSQL интеграция запускается только с `TEST_DATABASE_URL` на отдельной одноразовой тестовой базе. Она не была доступна в этом сеансе; успешная SQLite-проверка не объявляется подтверждением работы в Neon. Конфигурация Render/Neon сохранена. Факт публичного развёртывания и независимого ревью второго участника этим документом не утверждается.

## Ручной сценарий

1. На локальном стенде открыть регистрацию, создать вымышленный аккаунт, прочитать явное предупреждение об отсутствии SMS, подтвердить показанный код и войти.
2. Убедиться, что навигация показывает «Мои заявки». Создать заявку на будущий свободный интервал. В кабинете видна только эта заявка и ссылка на статус.
3. Выйти и создать второй тестовый аккаунт. В его кабинете чужих заявок нет. Гостевое бронирование по-прежнему доступно без входа.
4. На доске открыть учебный пример: фактическая доска остаётся отдельно. Скачать JSON/CSV/отчёт. Вернуться к рабочей доске и убедиться в сохранности её истории.
5. На отдельной тестовой карточке пройти соседние этапы. Пятый doing на команду, третий doing на человека, четвёртый review, третий testing и вторая срочная активная карточка отклоняются.
6. Done требует подтверждения всех пунктов, имени другого участника и ссылки. Никакой из этих проверок не подтверждает истинность введённой ссылки: ревью и стенд проверяются отдельно.

## Оставшиеся внешние шаги

Два спринта с реальными датами, реальная ретроспектива, независимое ревью, стенд и публикация требуют фактов и доступов команды. Браузерная доска подходит для одного источника данных и учебного экспорта, но не является серверным многопользовательским трекером. При необходимости перенесите те же политики в GitHub Projects, сохраняя историю в таблице с датами.
