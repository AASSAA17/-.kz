# План выпуска Semka.kz

Целевая среда полного MVP использует Render для Node.js, собранного интерфейса и API, Neon для PostgreSQL. Публикации `github-pages` относятся к статическим файлам. Даты и метрики этих сред ведутся раздельно.

## Окно и решение о выпуске

Предлагаемое регулярное окно в пятницу 18:00–19:00 по Астане (16:00–17:00 по Москве). До 18:20 выполняется развертывание и первичная проверка. До 18:40 оставляем время на восстановление. Последние 20 минут наблюдаем за приложением и закрываем запись релиза. Если к 18:00 нет зелёных проверок, резервной версии или второго участника, релиз переносится.

| Когда | Арсен | Адильжан |
| --- | --- | --- |
| Перед окном | Проверяет PR, артефакт и SHA, готовит сообщение о релизе | Проверяет переменные Render, состояние Neon, предыдущий Deploy ID и совместимость схемы |
| 18:00–18:20 | Даёт согласие, проходит сценарий клиента | Запускает Deploy a specific commit, проверяет API, журналы и PostgreSQL |
| 18:20–18:40 | При регрессии фиксирует время и проверяет результат отката | Выполняет Rollback, проверяет API и сохранность заявок |
| 18:40–19:00 | Обновляет статус выпуска и подтверждает UI | Проверяет логи, завершает запись Deploy ID, времени и результата |

## Чек-лист выпуска

1. Согласовать версию и окно, зафиксировать SHA из `main`, PR и успешный запуск CI именно для этого SHA. Скачать `semka-web-<SHA>`. Записать предыдущий успешный Render Deploy ID и SHA. Для первого запуска, когда предыдущего выпуска ещё нет, считать релиз пилотом и заранее согласовать остановку публикации при сбое.
2. Сверить в Render `NODE_ENV=production`, `DATABASE_URL`, `ADMIN_PASSWORD` и разрешённый HTTPS-origin. Секреты остаются в Render. В режиме ручных релизов проверить Auto-Deploy → Off. Для релиза с изменением схемы проверить восстановление на отдельной базе и убедиться, что старая версия приложения может читать расширенную схему. Иначе согласовать отдельное окно и сценарий восстановления данных.
3. В Render выбрать **Manual Deploy → Deploy a specific commit** и указать согласованный SHA. Записать время UTC и Deploy ID. После `Live` проверить `GET /api/health` и `GET /api/locations` на фактическом HTTPS-домене.
4. На демонстрационном стенде открыть каталог, выбрать будущий слот, создать заявку с вымышленными контактами, открыть страницу статуса и проверить отсутствие контактных данных. Проверить отклонение пересекающейся заявки, подтвердить и отменить тестовую заявку в админке, убедиться в освобождении слота. На production используйте только заранее согласованную тестовую площадку или согласованный тестовый слот. Учётные записи с демо-SMS выключены в production.
5. Зафиксировать статус, результаты smoke-проверок, ссылки на CI и Deploy ID. В сообщении о релизе указать версию, что изменилось, состояние сервиса и канал для обратной связи.

## Чек-лист отката

1. Остановить выпуск, если после прогрева повторяются ошибки `/api/health` или `5xx`, каталог или бронь недоступны, приняты две пересекающиеся заявки, либо открываются чужие данные. При подозрении на потерю или утечку данных решение об откате принимается сразу. Арсен записывает UTC начала воздействия, SHA, Deploy ID и симптом без персональных данных.
2. Адильжан открывает **Render → Deploys**, выбирает ранее проверенное успешное развертывание и подтверждает **Rollback**. Если его артефакт уже удалён, вручную развертывает известный рабочий SHA из репозитория после проверки совместимости схемы. Если подходящей версии нет, остановить пилот и согласовать восстановление с владельцем.
3. После `Live` Адильжан проверяет текущий SHA, `health`, каталог, подключение Neon и наличие сохранённых заявок. Арсен повторяет пользовательский сценарий и обновляет статус. При несовместимости схемы восстановить копию в отдельную ветку или базу Neon, сверить данные и согласовать переключение. Откат приложения сам по себе не восстанавливает содержимое Neon.
4. После подтверждённого восстановления записать UTC, время воздействия и итог. Открыть исправляющий PR, приложить ссылку на инцидент и занести его в журнал для DORA. Держать Auto-Deploy в режиме Off до нового согласованного выпуска.
