## Проверки перед слиянием

В корне проекта с Node.js 24 выполните `npm ci`, `npm run lint`, `npm test` и `npm run build`. На локальной машине PostgreSQL-тест пропускается без `TEST_DATABASE_URL`. CI проверяет его отдельно на одноразовой базе PostgreSQL 17. Для ручной проверки зависимостей используйте [OSV-Scanner 2.7.0](https://github.com/google/osv-scanner/releases/tag/v2.7.0) и команду `osv-scanner scan source --lockfile=package-lock.json`.

В Actions откройте `Semka CI`, проверьте `Node 24 / ubuntu-latest`, `Node 24 / windows-latest`, `PostgreSQL integration` и `Publish verified frontend`. Скачайте `semka-web-<SHA>` из Artifacts. Архив содержит клиентскую сборку Vite. Для полного MVP нужны сервер Node.js и база данных, для Render сборка выполняется по `render.yaml`.

Владелец `AASSAA17` открывает **Settings → Branches → Add branch protection rule** и указывает `main`. Правило требует PR, одно одобрение второго участника, повторное одобрение после изменений, закрытие обсуждений, актуальность ветки перед merge и успешные проверки с именами из первого прогона PR. Блокируются прямые обходы, force push и удаление ветки. Настройка доступна владельцу. После сохранения проверяющий открывает учебный PR и фиксирует состояния до одобрения и после одобрения. `AdilMoon` имеет право записи и может ревьюить PR Арсена. PR Адильжана ревьюит `AASSAA17`.

## Дашборд из GitHub API

```powershell
python -m pip install -r docs/labs/lz10/requirements.txt
python scripts/dora_dashboard.py --out dora-output
```

Период по умолчанию с 25 сентября по 5 ноября 2026 включительно, UTC. По окончании скрипт создаёт `dora-snapshot.json` с ID развертываний, статусами, SHA и временами, а также `dora-dashboard.png`. Перерисовать по сохранённым данным можно через `--snapshot <путь-к-JSON>`. Для более длинного периода может потребоваться read-only `GITHUB_TOKEN` в окружении. Скрипт не отправляет его в сторонние сервисы.

Данные по умолчанию относятся к `github-pages`. Успешные статусы определяют частоту. Lead time равен разнице между датой коммитера и временем первого наблюдаемого успешного развертывания коммита. GitHub Compare API даёт коммиты между соседними успешными развертываниями. Для первого наблюдаемого развертывания без предшественника учитывается только его SHA. Повторная публикация того же коммита входит в частоту и не дублирует lead time. Статусы `error` и `failure` показываются отдельно как технический индикатор.

Для расчёта CFR и времени восстановления передайте `--incident-log <файл.csv>` только после проверки полноты журнала по среде и периоду. Столбцы `deployment_id,impact_start_utc,restored_utc`. Одна строка на затронувшее пользователей развертывание. Если восстановление ещё идёт, последнее поле остаётся пустым. Для уже закрытых случаев дашборд показывает медиану. Полный журнал без инцидентов позволяет определить CFR как 0%, а для времени восстановления выборка остаётся пустой. Историю Render ведите отдельно. Чтобы читать её тем же скриптом, синхронизируйте фактические развертывания Render в GitHub Deployments под отдельным именем окружения и укажите его в `--environment`.
