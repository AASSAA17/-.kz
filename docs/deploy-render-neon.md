# Размещение MVP на Render Free и Neon Free

Схема: **браузер → HTTPS Render → Node.js → PostgreSQL Neon**. Один Render Web Service обслуживает интерфейс и API, а Neon хранит заявки, блокировки, сессии и журнал. Ниже — инструкция по настройке, а не сообщение о состоявшейся публикации. Фактический адрес сайта появится в вашем Render Dashboard.

## Стоимость и ограничения

Выбирайте **Free** у обоих провайдеров. В пределах бесплатных лимитов стоимость составляет $0. Neon Free предоставляет 100 CU-hours вычислений и 0,5 GB хранения базы на проект; контролируйте расход в консоли. Бесплатные лимиты могут меняться. [Neon: действующие возможности Free](https://neon.com/blog/neon-backend-is-ga), [тарифы Neon](https://neon.com/pricing).

Render Free засыпает после 15 минут без входящих запросов; пробуждение занимает примерно минуту. На workspace выделяется 750 бесплатных часов в месяц, также действуют лимиты трафика и сборок. При добавленном платёжном методе превышение части лимитов может тарифицироваться; без него сервисы или сборки могут приостановиться. Проверяйте Billing и оставайтесь на бесплатных планах. [Ограничения Render Free](https://render.com/docs/free).

Файлы Render Free теряются при перезапуске, повторном размещении или засыпании. Поэтому SQLite на Render не используется: данные находятся в отдельном Neon-проекте и сохраняются при этих событиях. Сохранность облачной базы не заменяет резервные копии и зависит от того, что проект и его данные не удалены. [Файловая система Render Free](https://render.com/docs/free#local-files-lost-on-redeploy).

Покупать домен не нужно: Render предоставляет поддомен `onrender.com` и HTTPS. [Домены и TLS](https://render.com/docs/tls). Условия проверены 25 сентября 2026 года; перед созданием ресурсов сверяйте тариф в интерфейсе провайдера.

## 1. Подготовьте Neon

1. Войдите в [Neon Console](https://console.neon.tech/) и создайте проект на плане **Free**.
2. Выберите доступный регион рядом с будущим регионом Render; в `render.yaml` указан Frankfurt. Для MVP достаточно одной базы и одной основной ветки; отдельные платные возможности не требуются.
3. Откройте **Connect**, выберите нужные ветку, базу и роль. Скопируйте строку подключения **Pooled connection**. Она содержит пароль — это секрет.
4. Сохраните строку для переменной `DATABASE_URL` на Render. Не помещайте её в README, `render.yaml`, GitHub, клиентский код или переменную с префиксом `VITE_`.

Используйте строку полностью вместе с параметрами TLS. Адаптер проекта проверяет TLS-сертификат и имя удалённого сервера; отключать проверку сертификата не нужно. Пример структуры, **не рабочие реквизиты**:

```text
postgresql://USER:PASSWORD@HOST/DATABASE?sslmode=verify-full
```

Интерфейс Connect и pooled-строка описаны в [руководстве Neon по подключению](https://neon.com/docs/connect/connect-from-any-app). Приложение само создаёт свои таблицы при запуске; вручную переносить SQL из SQLite в Neon не требуется.

## 2. Создайте сервис через Blueprint

Исходный код, `package-lock.json` и [render.yaml](../render.yaml) должны находиться в репозитории. Откройте [Deploy to Render](https://render.com/deploy?repo=https://github.com/AASSAA17/-.kz), войдите в свой Render-аккаунт и разрешите подключение нужного GitHub-репозитория. Проверьте создаваемые ресурсы: один **Web Service Free**, без платного диска и дополнительной базы Render.

Blueprint запросит **`DATABASE_URL`** — вставьте секретную pooled-строку Neon. **`ADMIN_PASSWORD` создаётся автоматически**. После создания сервиса откройте его **Environment**, найдите `ADMIN_PASSWORD` и сохраните значение для входа на `/admin`. Не публикуйте его. Значения `sync: false` и `generateValue: true` используются для запроса и генерации секретов без записи в Git. [Механизм секретов Blueprint](https://render.com/docs/blueprint-spec#prompting-for-secret-values).

Основные параметры уже заданы в `render.yaml`. Их также можно использовать при ручном создании через **New → Web Service**:

| Поле | Значение |
| --- | --- |
| Runtime / Language | Node, native runtime |
| Region | Frankfurt |
| Branch | Ветка с актуальным кодом MVP |
| Root Directory | Пусто, если `package.json` лежит в корне репозитория |
| Instance Type | **Free** |
| Build Command | `npm ci --include=dev && npm run build` |
| Start Command | `npm start` |
| Health Check Path | `/api/health` |

`--include=dev` устанавливает Vite для сборки, даже когда задан `NODE_ENV=production`. Во время работы Vite не запускается: Node.js отдаёт `dist/` и API. `npm run setup` на Render не нужен. Если выбираете ручное создание вместо Blueprint, заполните переменные из следующего раздела и задайте пароль самостоятельно. Порядок ручного создания описан в [Render Web Services](https://render.com/docs/web-services).

## 3. Задайте переменные окружения

Blueprint задаёт основные значения автоматически и запрашивает `DATABASE_URL`. Проверить или изменить их можно в **Environment** сервиса Render. Файл `.env` в репозиторий не загружайте.

| Переменная | Значение |
| --- | --- |
| `NODE_VERSION` | `24` |
| `NODE_ENV` | `production` |
| `HOST` | `0.0.0.0` |
| `DATABASE_URL` | Полная секретная pooled-строка Neon |
| `ADMIN_PASSWORD` | Автоматически создан Blueprint; при ручной настройке — случайный пароль от 12 до 256 символов |
| `ALLOWED_ORIGIN` | Обычно не нужен: берётся `RENDER_EXTERNAL_URL`; задайте вручную только для собственного домена или другого хостинга |

При ручной настройке пароль можно создать локально через `npm run setup` и взять из `.env`, либо сгенерировать менеджером паролей. При Blueprint используйте значение из Render Environment: оно отличается от локального `.env`. Сохраните пароль отдельно от публичных материалов.

Render задаёт `PORT` автоматически; приложение использует его. Не переносите локальное значение `PORT=3001` в настройки сервиса. `NODE_VERSION=24` фиксирует основную версию Node.js; способ задания версии описан в [документации Render](https://render.com/docs/node-version).

Render автоматически предоставляет `RENDER_EXTERNAL_URL` с фактическим HTTPS-адресом сервиса. Сервер использует его, если `ALLOWED_ORIGIN` не задан, поэтому вводить домен заранее или отключать проверку Origin не нужно. [Переменные Render](https://render.com/docs/environment-variables#render_external_url).

Если подключаете собственный домен, задайте `ALLOWED_ORIGIN` равным точному HTTPS-origin этого домена, без пути и завершающего `/`, и перезапустите сервис. Не указывайте `*`, адрес GitHub, Dashboard, localhost, список адресов или URL с `/admin`. После смены используйте сайт через выбранный домен: приложение разрешает один origin для изменяющих запросов. На другом хостинге, который не предоставляет `RENDER_EXTERNAL_URL`, `ALLOWED_ORIGIN` обязателен.

`NODE_ENV=production` включает `Secure` у cookie администратора и требует PostgreSQL и HTTPS-origin. Отдельную переменную `SECURE_COOKIE` задавать не нужно. Проверка `Origin` остаётся включённой: это часть защиты изменяющих запросов за HTTPS-прокси Render.

## 4. Проверьте размещение

1. Дождитесь успешного build и состояния работающего сервиса в Dashboard. В логах не должно быть ошибок подключения к PostgreSQL или отсутствующих переменных.
2. Откройте фактический HTTPS-адрес сервиса. Проверьте каталог и `/api/health`.
3. С вымышленными контактами создайте заявку на будущий свободный интервал, сохраните её ссылку.
4. На `/admin` войдите новым паролем, подтвердите заявку. Обновите клиентскую ссылку и проверьте статус.
5. Перезапустите сервис через Dashboard, затем проверьте ту же заявку. Она должна остаться в Neon.
6. После простоя учитывайте время пробуждения Render. Это ограничение Free, а не потеря заявки.

Проверки формы, занятых интервалов и блокировок приведены в [ручном сценарии](manual-smoke-test.md); замените localhost фактическим HTTPS-адресом. На этом этапе не вводите настоящие контактные данные клиентов.

## Данные, перенос и резервные копии

`DATABASE_URL` переключает приложение на PostgreSQL; `DB_PATH` в таком режиме не используется. Если соединение с PostgreSQL не удалось, приложение не переключается незаметно на локальную SQLite.

Neon начинает с отдельной базы. **Заявки, созданные ранее в локальном `data/semka.sqlite`, автоматически не импортируются.** Их перенос — отдельная задача. Демонстрационные площадки берутся из `server/locations.mjs` и появляются независимо от локальной базы. Первое размещение не должно добавлять вымышленные заявки под видом настоящих.

Не удаляйте Neon-проект, ветку или базу, если нужны содержащиеся в них заявки. Для важных данных настройте отдельные резервные копии PostgreSQL и проверьте восстановление. Не считайте возможность восстановления бесплатного тарифа бессрочной резервной копией.

## Частые ошибки

| Симптом | Что проверить |
| --- | --- |
| `vite` не найден при сборке | Build Command должен содержать `npm ci --include=dev` |
| Render не обнаружил порт | `HOST=0.0.0.0`; Start Command — `npm start`; приложение читает `PORT` Render |
| Требуется `DATABASE_URL` | Добавьте секретную строку Neon в Environment, затем перезапустите сервис |
| Ошибка подключения к базе | Проект и ветка Neon доступны, URL полный, пароль актуальный, TLS не отключён |
| Ошибка origin или 403 при отправке | Для onrender.com оставьте автоматический `RENDER_EXTERNAL_URL`; если задан `ALLOWED_ORIGIN`, он должен совпадать с фактическим HTTPS-доменом без завершающего `/` |
| Главная открывается, вход администратора не сохраняется | Используется HTTPS, задан `NODE_ENV=production`, origin совпадает с доменом |
| После простоя долго открывается первая страница | Подождите пробуждения Render Free; не создавайте дублирующую заявку |
| В облаке нет локальных заявок | SQLite и Neon — разные базы, автоматического переноса нет |

Если секрет попал в Git или публичную переписку, удаление строки из последнего файла не делает старое значение безопасным: замените пароль в Neon или Render. В отчётах об ошибках не публикуйте `DATABASE_URL`, `ADMIN_PASSWORD`, cookie или контактные данные.
