# Архитектура MVP

## Компоненты

```text
Браузер
  │
  ├─ разработка: React / Vite, 127.0.0.1:5173
  │                 └─ /api → 127.0.0.1:3001
  │
  ├─ локальная сборка: Node.js, 127.0.0.1:3001
                            ├─ статические файлы dist/
                            ├─ JSON API
                            └─ SQLite в data/

Размещение
Браузер → HTTPS Render → Node.js, 0.0.0.0:$PORT
                            ├─ статические файлы dist/
                            ├─ JSON API
                            └─ PostgreSQL Neon по DATABASE_URL
```

Node.js 24 используется и для сервера, и для инструментов разработки. Сервер работает на `node:http`. Без `DATABASE_URL` локальные данные хранятся через встроенный `node:sqlite`; отдельная установка базы или Docker не требуется. При наличии `DATABASE_URL` используется PostgreSQL через драйвер `pg`, а `DB_PATH` игнорируется.

В режиме разработки браузер обращается к `/api` через Vite-прокси. В собранном режиме интерфейс и API обслуживает один Node.js-процесс. Такой запуск позволяет проверить приложение на localhost без внешнего хостинга.

Для хостинга используется Render Native Node и отдельная база Neon. `NODE_ENV=production` требует `DATABASE_URL` и точный HTTPS-origin: из `ALLOWED_ORIGIN` или автоматически из `RENDER_EXTERNAL_URL`. Запуск production с SQLite запрещён, поскольку диск Render Free временный. Сервис связывает порт из `PORT` с адресом `HOST=0.0.0.0`. Порядок настройки приведён в [инструкции размещения](deploy-render-neon.md).

## Данные и время

Локации заполняются демонстрационными значениями. Бронирование связывает площадку, дату, временной интервал, контактные данные клиента и статус. Сервер повторно проверяет значения и стоимость: отображение доступности в браузере не является гарантией, что другой клиент не занял интервал между просмотром и отправкой формы.

Интервалы бронирования задаются в местном времени **Астаны (UTC+5)**. Часы в интерфейсе относятся к площадке, даже если клиент находится в другом часовом поясе. Аренда доступна с 09:00 до 21:00, шаг — один час, длительность — от одного до восьми часов. Можно выбрать сегодня или будущую дату в пределах 90 дней. Соприкасающиеся интервалы, например 10:00–11:00 и 11:00–12:00, не пересекаются.

## Жизненный цикл заявки

```text
pending ──→ confirmed ──→ cancelled
   ├──────→ rejected
   ├──────→ cancelled
   └──────→ expired
```

`pending` временно удерживает интервал на два рабочих часа. Рабочее окно — 09:00–21:00 по Астане; остаток срока переносится на следующее рабочее окно. Это время на обработку заявки, а не длительность аренды. `confirmed` сохраняет бронь. Отмена, отклонение и истечение срока освобождают интервал. Для отмены и отклонения нужна причина. Конечные статусы не восстанавливаются: при необходимости создаётся новая заявка с новой проверкой доступности.

Клиентская ссылка содержит случайный токен и показывает только сведения о бронировании, не раскрывая имя, телефон или комментарий. Ссылку всё равно следует считать частной: человек, которому она передана, может увидеть статус и время заявки.

## API

Ответы возвращаются в JSON. Для `POST` и `PATCH` нужен `Content-Type: application/json`, для всех изменяющих запросов — корректный `Origin`. Браузер передаёт его автоматически. В примерах ниже `:id` — идентификатор объекта, `:token` — токен из клиентской ссылки.

| Метод и путь | Назначение | Доступ |
| --- | --- | --- |
| `GET /api/health` | Проверка работы API | Открытый |
| `GET /api/locations` | Демонстрационный каталог | Открытый |
| `GET /api/locations/:id/availability?date=YYYY-MM-DD&duration=2` | Начало интервалов и доступность | Открытый |
| `POST /api/bookings` | Создание заявки | Открытый |
| `GET /api/bookings/:token` | Статус и условия заявки без контактов клиента | По токену |
| `GET /api/admin/session` | Проверка текущего входа | Открытый, без данных заявок |
| `POST /api/admin/login` | Вход: `{ "password": "…" }` | По паролю |
| `POST /api/admin/logout` | Завершение сессии | Администратор |
| `GET /api/admin/bookings` | Список; фильтры `status`, `date`, `q` | Администратор |
| `PATCH /api/admin/bookings/:id` | Новый `status` и при необходимости `reason` | Администратор |
| `GET /api/admin/blocks` | Заблокированное время | Администратор |
| `POST /api/admin/blocks` | Блокировка свободного интервала | Администратор |
| `DELETE /api/admin/blocks/:id` | Снятие блокировки | Администратор |
| `GET /api/admin/audit` | Последние 200 событий журнала | Администратор |

Создание заявки принимает `locationId`, `date`, `startTime`, `duration` (целое число часов), `name`, `phone`, необязательный `comment` и `consent: true`. Телефон нормализуется к формату `+7` и десять цифр. Цена рассчитывается на сервере, а не принимается из формы.

Заголовок `Idempotency-Key` при создании заявки должен содержать UUID. Повтор того же запроса с тем же ключом возвращает существующую заявку и не создаёт дубль. Тот же ключ с другими данными приводит к `409 IDEMPOTENCY_CONFLICT`. Занятый интервал возвращает `409 SLOT_UNAVAILABLE`. Новая заявка получает HTTP 201, повтор — HTTP 200.

Для блокировки передаются `locationId`, `date`, `startTime`, `duration` и `reason`. Заблокировать уже занятый заявкой интервал нельзя. Ошибки имеют поля `error` с понятным текстом и `code` для программной обработки. Основные статусы: 400 — неверные данные, 401 — нет доступа, 403 — запрещённый источник, 409 — конфликт, 429 — превышение числа попыток входа.

## Локальные секреты и хранение

`scripts/setup.mjs` создаёт `.env` через эксклюзивное создание файла и не перезаписывает существующий файл. Пароль генерируется из криптографически случайных байтов. `.env` и `data/` исключены из Git. `.env.example` содержит только имена настроек и не содержит действующего пароля.

Администратор входит по одному паролю, заданному в `ADMIN_PASSWORD`. Сервер выдаёт сессионную cookie с `HttpOnly` и `SameSite=Strict`; срок сессии — восемь часов. Изменяющие запросы проверяют `Origin`. Vite-прокси сохраняет исходный `Host` (`changeOrigin: false`), чтобы эта проверка работала в разработке. Не отключайте её для устранения ошибки настройки прокси.

После пяти неверных попыток входа с одного IP следующие попытки ограничиваются до конца 15-минутного окна. Состояние ограничения, сессии и журнал сохраняются в выбранной базе. Их наличие не заменяет проверку защиты от распределённых злоупотреблений. Для localhost `ALLOWED_ORIGIN` не нужен. На Render сервер берёт точный origin из автоматически предоставленного `RENDER_EXTERNAL_URL`; `ALLOWED_ORIGIN` переопределяет его для собственного домена. На другом хостинге этот параметр нужно задать вручную.

При `NODE_ENV=production` cookie получает `Secure`; отдельной настройки `SECURE_COOKIE` нет. Render завершает TLS на своём прокси, а точный `ALLOWED_ORIGIN` позволяет проверять исходный HTTPS-адрес без отключения защиты от запросов с другого сайта. `DATABASE_URL` и пароль администратора хранятся только на сервере, не передаются через `VITE_` или публичные файлы сборки.

PostgreSQL подключается через небольшой пул (до пяти соединений), включая pooled endpoint Neon. Для удалённой базы адаптер требует проверку TLS-сертификата и имени хоста. Таблицы создаются при запуске, повторный запуск не очищает данные. Ошибка подключения не приводит к автоматическому переключению на SQLite.

`scripts/dev.mjs` запускает сервер и Vite как дочерние процессы без отдельного терминала. При остановке или завершении одного процесса он завершает другой. На Windows завершение ограничено деревьями запущенных дочерних процессов.

При резервном копировании остановленного приложения сохраняйте всю папку `data/`. Если приложение работает, копирование одного файла SQLite без согласованной процедуры резервного копирования может пропустить данные WAL.

Копия папки `data/` относится только к SQLite. Neon — отдельное хранилище; локальные заявки автоматически туда не импортируются. Для PostgreSQL нужны свои резервные копии и проверка восстановления. Каталог демонстрационных площадок загружается из кода и не зависит от переноса заявок.

## Ограничения перед публикацией

- Локальный адрес `127.0.0.1` предназначен для одного компьютера. Для Render предусмотрены production-настройки; это не отчёт о проверке безопасности публичного сервиса.
- Администратор использует общий локальный секрет; индивидуальные учётные записи, роли и восстановление пароля не реализованы. Журнал операций MVP не заменяет полноценную систему аудита.
- Render предоставляет HTTPS; конфигурация включает Secure-cookie и точный origin. Перед настоящей эксплуатацией остаются проверки защиты от злоупотреблений и правила управления секретами.
- Демонстрационные контактные данные не подтверждают согласие настоящих клиентов на обработку данных. До реальной эксплуатации нужны согласованные правила сбора, хранения, доступа и удаления.
- Нет интеграции с оплатой, SMS, почтой, CRM и календарями. Создание заявки не подтверждает получение оплаты или согласование с реальным владельцем площадки.
- Нагрузочные характеристики, восстановление после сбоев и соответствие всему перечню требований ЛЗ требуют отдельных измерений. Этот документ не является отчётом о проведённых нагрузочных или защитных испытаниях.

SQLite упрощает локальный запуск, PostgreSQL отделяет данные размещённой версии от жизненного цикла Render. Бесплатный Render засыпает при простое, поэтому этот вариант подходит для демонстрации, но не обеспечивает постоянную готовность сервиса. При масштабировании нужны отдельные проверки конкурентных запросов, мониторинг и развитие управления доступом.
